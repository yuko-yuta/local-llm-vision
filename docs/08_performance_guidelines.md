# Gemma4 画像認識Webアプリ - パフォーマンス方針

## 画像サイズ最適化

| 用途 | 最大幅 | JPEG品質 | 理由 |
|---|---|---|---|
| 通常認識（アップロード） | 1024px | 0.8 | 精度重視 |
| 通常認識（カメラ撮影） | 1024px | 0.8 | 精度重視 |
| リアルタイムOCR | 640px | 0.7 | 速度重視 |

## リアルタイムOCR設定

| 項目 | 値 | 変更可否 |
|---|---|---|
| OCR間隔 | 2秒 | 調整可（重い場合は3秒に） |
| 同時リクエスト数 | 最大1件 | 変更不可（設計上の制約） |
| タイムアウト | 15秒 | 変更可 |
| 前回結果との比較 | 同一文字列なら更新しない | 変更不可 |

## PC負荷を下げるための工夫

1. **前回OCRが完了するまで次のリクエストを送らない**
   - `isOcrRunningRef` で制御
   - setInterval + refフラグの組み合わせで実装

2. **画像を縮小してから送信**
   - Canvas APIで `maxWidth` にリサイズしてから base64化
   - Ollamaへの転送データ量を削減

3. **前回と同じ文字列なら画面更新しない**
   - Reactの不要な再レンダリングを防ぐ
   - `realtimeText` stateとの比較で判定

4. **カメラ停止時にOCRループを止める**
   - `clearInterval` でタイマーを破棄
   - バックグラウンドでのリクエスト送信を防ぐ

## Ollama・Gemma4のスペック目安

| 環境 | 1回の認識時間目安 |
|---|---|
| GPU (RTX 3060以上) | 1〜3秒 |
| CPU (Core i7相当) | 5〜15秒 |
| CPU (低スペック) | 30秒以上 |

- CPU環境では2秒間隔のOCRは重すぎる場合がある → 3〜5秒に変更推奨
- OCRが間に合わない場合: 前のリクエストが完了するまで次は送らない設計のため自動的に間隔が広がる

## 画像サイズとbase64の関係

| 元画像 | 縮小後 | base64サイズ概算 |
|---|---|---|
| 4K (3840x2160) | 1024px幅 | 約200〜400KB |
| FHD (1920x1080) | 1024px幅 | 約150〜300KB |
| カメラOCR用 | 640px幅 | 約50〜150KB |

小さいほどOllamaへの転送・推論が速くなる。
